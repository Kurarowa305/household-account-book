# フロントエンドテスト観点

## 目的

現状の `frontend/` 配下実装をCIで自動確認するためのテスト観点を定義する。

このドキュメントでは、画面実装、hash route、mock ViewModel、in-memory Action、Design Portalとの同期を主な確認対象にする。API、adapter層、DB、localStorage永続化、実PDF出力、実LINE連携は未実装のため、現時点のテスト対象外とする。

## 前提

- アプリ本体は `frontend/index.html` を入口にした素のHTML/CSS/JavaScriptのSPAである。
- 画面切り替えは `frontend/js/constants/routes.js` と `frontend/js/router.js` のhash routeで行う。
- 各画面は `frontend/js/pages/` の `render*Page(viewModel)` でHTML文字列を返す。
- 一部画面は `mount*Page(root, viewModel)` でcanvas描画などのDOM依存処理を行う。
- 表示データは `frontend/js/mocks/` と `frontend/js/utils/ledgerCalculations.js` 由来のmock ViewModelで作る。
- Actionは `frontend/js/actions/` と `actionDispatcher.js` でin-memory stateを更新し、外部通信は行わない。
- `design/portal/` は `frontend/js/pages/` の描画関数を直接importしてプレビューする。

## 優先度

| 優先度 | 位置づけ | CIでの扱い |
| --- | --- | --- |
| P0 | 画面実装の破損をすぐ検知する最低限の観点 | 初期CIから必須 |
| P1 | 主要操作、計算、設計ポータル同期を広く守る観点 | P0整備後に追加 |
| P2 | 見た目、アクセシビリティ、将来層を含む補強観点 | 必要に応じて追加 |

## 自動化スクリプト

P0観点は `frontend/script/test.mjs` で自動化し、以下のコマンドで実行する。

```sh
npm run test:frontend:p0
```

## テスト分類

| 分類 | 主対象 | 主な検出内容 |
| --- | --- | --- |
| 静的整合性テスト | route、registry、CSS import、module import | 参照切れ、UID重複、metadata不整合 |
| ユニットテスト | router、formatters、ledgerCalculations、Action関数 | 計算誤り、state更新誤り、境界値漏れ |
| レンダリングテスト | page/componentのHTML出力 | 画面UID欠落、Action UID欠落、表示崩れの前兆 |
| ブラウザE2Eテスト | `frontend/index.html` | route遷移、フォーム操作、クリック操作、console error |
| Design Portalテスト | `design/portal/index.html` | frontendとの同期漏れ、inspector表示不備 |

## CI導入時の推奨順

1. 静的整合性テスト: import可能性、route/registry整合性、UID重複、参照ファイル存在を確認する。
2. ユニットテスト: router、formatters、ledgerCalculations、Action関数をDOM依存の少ない順に確認する。
3. Frontend browser smoke: ローカルHTTPサーバーで全routeを開き、console errorと主要DOMを確認する。
4. 主要Action E2E: Port Keys、Shopping List、Reports、Walletsの代表操作を1本ずつ確認する。
5. Design Portal smoke: 全screen preview、Component詳細、Action詳細、Computed Style表示を確認する。

## テストデータ方針

- 各テストは `appMockState` を直接共有せず、テストごとにdeep cloneしたstateを使う。
- `Date.now()` と `Math.random()` に依存するIDは完全一致で検証せず、prefix、追加件数、保存内容を検証する。
- 年月は既存mockの `2026-05` と `fiscalYear: 2026` を基準にする。
- ブラウザE2Eではテスト間でページをreloadし、in-memory stateの持ち越しを避ける。
- CIでは外部networkに依存しない。lucide CDNが読み込めない場合でも、画面本体が描画できることを確認する。

## API/adapter実装後に追加する観点

| 観点 | 追加確認内容 |
| --- | --- |
| adapter契約 | Actionから直接APIを呼ばず、adapter経由でrequest/responseを扱う。 |
| loading/error | 保存、削除、出力、送信中のloading表示と失敗時メッセージを確認する。 |
| 永続化 | reload後もwallet、entry、shopping item、commentの状態が復元される。 |
| バリデーション | client validationとserver validation errorの表示差分を確認する。 |
| 権限 | view roleのwalletで編集/削除操作が制限される。 |
| PDF/LINE連携 | 実PDF生成、LINE送信、スケジュール実行は外部連携をmock化した契約テストと、本番連携の限定E2Eに分ける。 |

## 対象外

- `backend/`、`infra/`、`prototype/` の実装テスト。
- API、adapter、DB、localStorage永続化の成否。
- 実PDFファイルの生成内容。
- 実LINE送信の到達性。
- React、Vue、Angular、TypeScript、Tailwind CSS、Vite、Next.jsなどの導入を前提にしたテスト構成。
